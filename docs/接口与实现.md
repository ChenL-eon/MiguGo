# 接口与实现

本文承接 [README](../README.md)，记录不在首页展开的实现细节：原生登录协议、搜索分页与免费取链、VIP 取链、播放音质、歌词取址、官方网页播放器、首页推送、账号歌单、外部歌单导入、登录方式与账号状态，以及合规实现约定。

应用只对接咪咕面向网页端公开的接口，按用途分为搜索、歌单、播放取链、首页推荐、登录与会话交换；实现集中在 `lib/services/api/` 与 `lib/services/auth/`。这些接口属于非官方公开网页接口，可能随时调整或限制访问。

## 原生登录协议

登录链路的请求依次发生，除公钥外都带 `Referer: https://passport.migu.cn/login` 与 `Origin: https://passport.migu.cn`：

1. `POST /password/publickey` 取 `result.modulus` 与 `result.publicExponent`（均为 16 进制字符串）。公钥每次登录重新取，官方会轮换。
2. 用取到的 modulus 与指数对输入做 RSA（PKCS#1 v1.5 type-2 填充，输出小写 16 进制、不补齐宽度），与官方网页的 jsbn 实现逐位一致；纯 Dart 用 `BigInt.modPow` 完成，见 `lib/services/auth/migu_rsa.dart`，没有引入额外依赖。
3. `POST /authn`（`loginID` + `enpassword`，`imgcodeType=1`、`appType=0`、`relayState=`）或 `POST /authn/dynamicpassword`（`msisdn` + `dynamicPassword`，`imgcodeType=2`、`securityCode=7619`）；发短信用 `GET /login/dynamicpassword`。`sourceID=220029`、`isAsync=true`、`fingerPrint`/`fingerPrintDetail`（应用启动时生成的 32 位随机 16 进制串，整个运行期间复用，官方用它当浏览器指纹，本机不采集任何真实指纹）是表单常量。成功返回 `status=2000` 与 `result.token`。
4. 被风控时先补两步图形验证码，然后回到第 3 步重投一次：
   - `GET /captcha/graph/risk?imgcodeType=&showType=&sourceid=220029` 取图。响应的 `result.captchaurl` 本身就是 `data:image/jpeg;base64,…` 图片，应用剥掉前缀还原成字节显示在表单里，`imgcodeType` 沿用登录方式的编号（1=账号密码、2=短信），`showType` 0 是首次加载、1 是官方页面的「换一张」。响应同时用 `Set-Cookie` 下发 `mgnd_session_id` 等通行证会话 Cookie，验证码答案就记在这份会话上，取图、校验与随后的登录必须共用同一份，否则等于每次重新回答。
   - `GET /captcha/graph/check?imgcodeType=&captcha=&sourceid=220029` 把用户照图输入的字符**明文**交给官方认一次，不对时返回 `4002 验证码错误或已失效`，界面提示换一张重填。认过之后才重新提交登录，登录表单里的 `captcha` 同为用户输入的明文。

   这条链路里的图片始终原样显示、答案始终由人输入，应用不做任何识别或自动作答。咪咕若改要滑块（`/captcha/sliding`，官方 `getability` 脚本在账号被判定存在安全风险时下发这条路径）等本表单呈现不了的形式，只做提示并引导改用官方页面。
5. `GET user/h5/token-validate/v3.0?token=&type=2&sourceId=220029&activityId=MUSIC-WWW`，请求头带 `Cookie: idmpauth=true@passport.migu.cn`，由 `Set-Cookie` 拿到 `pacmtoken`——原生 VIP 取链唯一需要的凭据。只有这一步成功才算登录完成。写进安全存储的是这一步下发的 `pacmtoken` 与本次登录票据：前者用于取链；后者不随普通请求发送，也不再参与失效判定——这张票就在这一次换票里被咪咕消耗掉了，换不来第二个会话（2026-10-26 真机确认），本机留着它只为了在调试版里当场复测一次，退出登录时一并删掉。

登录用的 Dio 与全局网络层完全分开：不携带本机旧的 `pacmtoken` 与统计 Cookie，一次失败的登录不会污染已有会话。通行证会话 Cookie 只在这一份 Dio 实例的内存里按域名保存，只发给 `passport.migu.cn`，换票请求仍然只带 `idmpauth` 那一条声明，且不落盘。失败提示只包含自己组织的中文文案与咪咕返回的状态码，绝不回显密码、验证码、票据或 Cookie 值；接口调整或验证码做不到时，界面会明确引导改用「使用咪咕官方页面登录」。

## 搜索分页与免费取链

单曲搜索还有一个固定行为：`pageSize` 传 20、30、50 或 100，响应都只返回 20 条，只有 `pageNo` 生效。应用因此固定按 20 条一页请求，并在结果底部用 `pageNo + 1` 追加下一页，同时对 `contentId` 去重。

`listenSong.do` 的实测行为（同一请求只更换曲目与是否携带 Cookie）：

| 曲目 | 是否携带 Cookie | 返回 |
| --- | --- | --- |
| 免费曲目（如断桥残雪） | 任意 | `302` + `Location` 明文时效地址 |
| VIP 曲目（如孤勇者、普通朋友、我的地盘） | 携带有效 Cookie | `200` + `{"code":"200002","info":"PE参数格式错误"}` |
| 同上 | 完全不携带 Cookie | 与上一行**逐字相同** |

这条接口只为免费曲目发放地址，VIP 曲目的拒绝与本机登录状态无关，因此 VIP 曲目改走网页播放器使用的策略接口。应用把 `200002` 归类为“接口不发放该曲目地址”，不提示“登录可能已失效”，也不改变账号状态。

## VIP 曲目：原生取链

VIP 曲目使用咪咕网页播放器自己的取链接口：

`GET https://app.c.nf.migu.cn/strategy/pc/listen/v2.0?scene=&netType=01&resourceType=2&copyrightId=<id>&contentId=<id>&toneFlag=<PQ|HQ|SQ|ZQ24>`

- 请求头除 `Referer` 与 Cookie 外，还带本机 `uid` / `pacmtoken` / `msisdn`，以及站点用来判断是否编码响应的 `signature: 1`、`birth: h5page`。
- 响应体是站点自己的编码：4 字节头 `AB CD 01 <偏移>`，正文逐字节为 `明文 + 偏移 - 密钥`，密钥随网页 SDK 下发。`lib/services/api/migu_response_cipher.dart` 只负责还原这层 JSON 信封，**不涉及音频文件解密**。
- 从「设置 → 播放 → 播放音质」选择的档位开始，按 `ZQ24 → SQ → HQ → PQ` 逐级回退；是否发放地址、发放哪一档完全由咪咕按账号权益与曲目母带情况决定。`data.audioFormatType` 是服务端实际发放的档位，请求 ZQ24 也可能静默返回 SQ/HQ。
- 没有地址时，接口会在 `data.dialogInfo.text` / `data.cannotCode` 里给出原因（实测匿名请求 VIP 曲目 HQ 返回 `440022`“会员专属音质，请先登录”，非会员请求 VIP 曲目 ZQ24 返回 `440008`“开通会员后即可无限畅享”），应用直接转述这段文案，并在提示中列出已尝试的档位；需要单独购买的数字专辑同样由服务端拒绝。
- 播放地址只交给 `just_audio` 在线流式播放，不下载、不落盘。

## 播放音质

| 档位 | 咪咕标识 | 设置页文案 | 说明 |
| --- | --- | --- | --- |
| 标准音质 | `PQ` | 标准 | 约 128 kbps，免费曲目的兜底档位，无需登录即可请求。 |
| 高品质 | `HQ` | 高品质 | 约 320 kbps，由账号权益决定是否发放。 |
| 无损音质 | `SQ` | 无损 | FLAC 无损，由账号权益决定是否发放。 |
| 至臻音质 | `ZQ24` | 至臻 | FLAC 24bit，需曲目提供 24bit 母带且账号有对应权益；免费曲目也可能发放。 |

- 默认「高品质」。免费曲目在未登录时直接走 `listenSong.do` 的标准音质；已登录并选择更高档位时，先尝试策略接口，失败后自动回退 `listenSong.do`，保证仍能试听。
- VIP 曲目从所选档位开始逐级回退；没有任何可用地址时给出服务端原因与已尝试档位，并保留「官方播放器」兜底。
- 设置项会持久化到本机；切换后从下一首开始生效，正在播放的歌曲不会被打断。
- 实际音频以咪咕发放的为准；播放页不额外标注码率，避免把服务端结果误报成“已获得无损/至臻”。

## 歌词取址与解析

- 优先使用歌曲条目自带的 `lrcUrl`；没有地址，或拉到的文本不是带 `[mm:ss]` 时间戳的同步歌词时，改用 `GET https://app.u.nf.migu.cn/MIGUM2.0/v1.0/content/resourceinfo.do?resourceId=<contentId>&resourceType=2`，从响应的 `resource[0].lrcUrl` 取歌词地址。
- 资源接口也没有可用地址时，才退回原来的公开搜索：按「歌名 + 首位歌手」搜索，优先匹配同一 `contentId`，其次匹配同名且有歌词的条目。
- 三个来源按顺序尝试，同一个地址只拉取一次；歌词地址统一经 `resolveMiguAssetUrl()` 补全并把 `http://` 升级为 `https://`，拼写错误或非同步歌词不会被当作成功结果。
- 歌词资源属于公开接口：401/403 只表示这条资源拿不到，不参与登录失效判定；所有来源都失败时返回空结果，由播放页显示「暂无同步歌词」。
- `LyricParser` 只解析逐行 LRC，支持一行多个时间标签和同时间点双语合并；不解析逐字 MRC，也不做翻译歌词。

## 官方网页播放器

如果原生取链被咪咕拒绝，播放页仍提供「官方播放器」面板作为兜底——它是咪咕自己的页面，登录、鉴权、取链都在页面里完成：

- 地址为 `https://music.migu.cn/v5/#/playlist?search=<歌名>&playlistType=ordinary`。v5 是 hash 路由的单页应用，路由只有 `musicLibrary`、`playlist`、`albumDetail`、`singerDetail` 等，**没有歌曲详情页**，`music.migu.cn/v3/music/song/<id>` 之类旧地址一律 301 回 `/v5/`，搜索结果页是唯一直达某一首歌的入口。
- 歌名取自接口返回的 `songName`，会先去掉括号（`(`、`（`、`[`、`【`）及其后面的括注，否则「孤勇者(《英雄联盟：双城之战》主题曲)」整串搜索反而找不到。
- Windows 上面板使用独立的用户数据目录 `%LOCALAPPDATA%\migu_lele\webview2_player`，与官方登录窗口的 `webview2` 隔离：登录窗口进出时会清空自己那份 Cookie，不能连带抹掉播放页里咪咕写入的登录会话；Android 没有独立目录，两处共用系统 WebView 的 Cookie 库。
- 面板只加载 `https://*.migu.cn` 的页面，其余跳转一律取消；不执行 `evaluateJavascript`，不解析页面内容，也不读取音频地址。用户在这个页面里点咪咕的「登录」，用咪咕自己的方式登录，权限判定完全在咪咕服务端。
- Windows 上登录会话由 `WebSessionSync`（`lib/services/auth/web_session_sync.dart`）在面板与原生请求之间双向同步（Android 不支持，`WebSessionSync.supported` 为假，网页会话只留在系统 WebView 里）：`onLoadStart` 时把本机手动快照里登录相关的名称（`mg_auth_*`、`pacmtoken` 等）写进 profile，`onLoadStop` 后从 profile 读回并只更新网页会话类的名称（`mg_auth_sid` 等），让官方页面续签出的新会话顺带给本机续期；读回**不接受认证凭证**（`pacmtoken`、`mg_auth_pacmtoken`）——profile 里读到的那一份分不清是刚续签的还是退出前残留的，咪咕又不给凭证版本，按到达顺序覆盖就可能把官方校验接口刚确认过的新值换回旧值，凭证只由轮换与服务端 Set-Cookie 两条通道更新。写读都带 6 秒超时，且发生在 WebView 已创建之后，避免 `CookieManager` 在无 WebView 实例时挂住；同步失败只跳过这一次，不影响页面。

## 首页推送

- 每日推荐：`GET https://app.c.nf.migu.cn/pc/v1.0/template/todayRecommendList/release?actionId=1&index=1&templateVersion=5`，读取 `data.recommendData.data`，其字段与搜索接口一致，可直接映射为歌曲模型；`time` 字段是推荐日期。
- 精选歌单：`GET https://app.c.nf.migu.cn/pc/bmw/page-data/music-index-show/v2.0?templateVersion=1`，取 `view == 'ZJ-SongList-Scroll'` 的栏目，解析其中的 `resId`、`txt`、`img` 作为歌单卡片。
- 推荐结果由咪咕按当天与账号状态下发，应用不做本地排序或个性化推断；未登录时返回的是匿名推荐。

## 账号歌单

登录后歌单页顶部的「我的音乐」只读展示账号自己的歌单，不新建、不收藏、不修改账号内容：

- `GET https://app.c.nf.migu.cn/pc/user/home-page/v2.0`：从 `userPrivateItems` 里找 actionUrl 含 `musicListId` 的「喜欢的音乐」入口，并读取 `myCreatedMusicLists.createdMusicLists` 与 `myCollectedMusicLists.collectMusicLists`。
- 点开任意歌单后复用公开歌单详情与歌曲接口（`resource/playlist/v2.0`、`MIGUM3.0/resource/playlist/song/v2.0`），按页加载、整单播放。
- 结果只留在内存里：登录成功（含带凭据启动）时自动读取一次，退出登录即清空，不写入本机偏好文件。

## 外部歌单导入

歌单页的「我的导入」只接受用户粘贴的公开分享链接，流程为：解析链接 → 读取外部歌单的曲目名与歌手 → 逐首搜索咪咕曲库 → 保存匹配结果。

| 平台 | 读取方式 | 实测限制 |
| --- | --- | --- |
| 网易云音乐 | `GET https://music.163.com/api/v6/playlist/detail?id=<id>&n=1000`（Referer `https://music.163.com/`） | 不带 `n=1000` 时匿名请求只返回前 10 首完整曲目；带上后返回整个歌单（实测 200 首）。 |
| QQ音乐 | `GET https://c.y.qq.com/qzone/fcg-bin/fcg_ucc_getcdinfo_byids_cp.fcg?disstid=<id>&…`（Referer `https://y.qq.com/`） | 缺少 Referer 返回 `invalid referer`；实测 393 首完整返回。 |
| 酷狗音乐 | `GET https://www.kugou.com/yy/special/single/<id>.html` | 网页版只公开前 30 首，页面出现「查看更多内容」时按部分导入并在界面标明；本机环境下 `mobilecdn` 接口证书无效，因此未使用。 |

- 短链接（`163cn.tv`、`c6.y.qq.com/base/fcgi-bin/u`、`k.kugou.com`）先跟随 302，再从最终地址或页面正文中提取歌单 ID。
- 匹配先做标题归一化（去括号注释、`feat.`、全半角与标点差异），标题完全一致优先；包含匹配必须同时有歌手重合，避免把翻唱或同名曲当成原曲。
- 单次最多扫描 500 首（并发 4），最多保存 20 个导入歌单，按来源链接去重；结果保存在本机 SharedPreferences。匹配途中遇到咪咕限流会立即停下并提示稍后再试，本次不保存。未匹配的曲目会列在导入歌单页底部，不会被静默丢弃。

## 登录方式与账号状态

入口只有一个：桌面左下角的账号卡片，或移动端「我的」页的「账号与播放权限」。点开就是 `lib/widgets/account_center.dart` 这个弹窗——未登录时它内嵌原生登录表单（`lib/widgets/native_login_panel.dart`），已登录时同一屏改成简约版个人中心：头像、昵称、打码手机号、VIP 标识，以及登录凭据项数、登录时间、最近校验时间和播放权益说明，底部是「切换账号」与「退出登录」两个按钮。已经没有独立的登录入口页；系统浏览器登录与手动粘贴 Cookie 两个功能整体删除，对应的 `login_page.dart`、`account_login_card.dart`、`cookie_login_actions.dart` 与 `native_login_page.dart` 一并移除。

### 退出登录与切换账号

两个按钮走同一段逻辑：先清掉安全存储里的登录凭据、登录票据与服务端会话快照（`MiguCookieStore.clearLoginCookies()` 与 `PassportTicketStore.clear()`），把本地登录状态归零并停掉前台保活（`AccountProvider.signOut()`），再停止播放、清空播放列表与歌词（`PlayerProvider.clearQueue()`），同时注销系统媒体控制。区别只在退出之后停在哪一屏：「切换账号」留在弹窗里，此时 `hasLogin` 为假，原生登录表单就地出现，直接登新账号；「退出登录」关掉弹窗并在首页提示「已退出登录，本机保存的凭据已清除」。两个动作都要先过一个确认弹窗，说清清除范围。

咪咕没有登出接口，这一步只发生在本机：服务端那份 `pacmtoken` 在它自己眼里仍然有效，应用不会、也无法通知它。登录票据同样被删掉，不会留到下一个账号。设置、搜索历史与导入的歌单都不在清除范围内；重新登录一次同样会整体覆盖旧凭据。

### 登录失效时自动退出

除手动退出外，还有一种应用自己发起的退出，但它需要**两次独立取证**才生效。判定在 `MiguApiClient._noteFailure()` 里做，因为只有拦截器拿得到真实请求地址（`290001 请先登录` 是 HTTP 200 带回来的）：条件是本机确实带过 `pacmtoken`，且这条回绝说得出凭据本身的事。说得出的只有两个地方：一是 `isLoginScopedEndpoint()` 认下的账号接口（`/user/h5/user-info/`、`/pc/user/home-page/`、`/pc/user/h5/queryUserInfo/`）**且本机确实有 `uid`**——2026-10-25 实测，这三个接口对「不带凭据」「只带假 `pacmtoken`」「假 `pacmtoken` 再加 `uid`」回的都是同一句 `290001 请先登录`，缺 `uid` 时它分不清是凭据过期还是这份凭据集不够用，原生登录只带 `pacmtoken`，所以这些回绝只留证据；二是 `isSessionValidatorEndpoint()` 认下的官方会话校验接口 `/mgateway/api/checkPacMtoken`，它只看 `pacmtoken` 一份凭据（不带凭据回 `850001 未登录`，看不懂的乱值回 `850003 内部错误`，会话超时回 `850005 登录超时`），`sessionValidatorRevokedCodes` 里的 `850001` / `850005` 就是这份凭据被拒的直接结论，不需要 `uid` 也成立；`850002` / `850003` 那种「内部错误」是它自己的问题，不算。任一条件满足时 `SessionRejectLedger.note()` 记一条证据并计一次数，再走 `AccountProvider.markSessionRevoked()`：计数不足 2 就只调 `markRejected()` 把状态降级为「登录可能已失效」，**凭据原样保留**；计数到 2 才确认作废：停掉前台保活，通过 `AccountProvider.onAutoSignOut`（在 `main.dart` 里接到 `signOut()` + `PlayerProvider.clearQueue()`）执行与手动退出完全相同的一套动作，并在登录面板顶部把原因写清楚：状态标签变成「登录已失效，已自动退出」，说明文字点名是咪咕拒绝了本机凭据、不是用户自己退的，还附上最近一次被拒的接口地址、HTTP 状态码与业务编码。左下角那张账号卡片此时也跟着换成同一句「登录已失效，已自动退出」和警示色图标，不藏着让用户以为是自己的正常未登录状态。这条说明只在重新登录时收起。

判定这条线路上**不再有用留存票据换一次新会话这一步**，2026-10-26 才把它摘掉。原先的流程是先后台 `MiguPassportApi.renewSession()`，换到了清零计数继续用，换不到才进上面那套两步判定。真机把它证伪了：票据在登录那一次换票时就被咪咕消耗掉，第二次同样请求回的是 `HTTP 200, 票据码 199999`、不下发新 `pacmtoken`——连刚签发几十秒的票都一样，所以这一步永远换不来新会话（见「登录探测诊断」一节）。留着它不只是白发一个请求：这种回包按失败分级属于「暂时失败」，`_renewSession()` 只会调 `markRejected()`，而 `markSessionRevoked()` 把裁决交给它之后就返回了，两次取证的作废分支根本没跑到。表现就是用户实际遇到的样子——凭据早就死了，界面长期停在「登录可能已失效」，怎么都不自动退出，每首歌都要重新登录的提示。现在 `markSessionRevoked()` 只做两步判定，`_renewSession()` 与票据存储一起留给调试入口复测（`AccountProvider.debugRenewNow()`）。

同样的分寸也用在建会话探测上：`MiguMusicApi.checkSessionAlive()` 先走官方校验接口，再用账号资料兜底。兜底那条只有在**官方校验接口没给出结论**、且本机带得出 `uid` 时，它的 `290001` 才被当作失效证据；原生登录缺 `uid` 时这一次探测只报 `unknown`，界面保持原状，探测记录里写一句「账号资料回绝，但本机没有 uid，不计为失效」。反过来，校验接口自己回 `850005 登录超时` 时不需要 `uid` 也算结论——2026-10-26 的第一条真机记录就是这一句：前一晚 `000000` 通过并轮换过 token，次日开机回 `850005`，同时账号资料与歌单都读不出东西、VIP 取链拿不到播放地址。启动探测判为 revoked 时 `main.dart:_warmUpSession` 直接调 `AccountProvider.markSessionRevoked()`，当场进入两步判定，不再干等下一次保活（45–75 分钟）；资料与歌单交给那条路径自己刷，免得用旧凭据并发盖掉判定结果。

两次之间必须隔开 `SessionRejectLedger.confirmGap`（默认 30 分钟）：登录后的批量请求里，多个账号接口会因为同一个原因同时被拒，那是一波失败而不是两次独立取证。计数同时只在 `strikeWindow`（默认 24 小时）内有效：启动读回或写入下一条证据时，超过窗口的旧账一律作废，否则几天前的一次拒绝会和新启动时的第一次拒绝凑成「确认失效」，表现为刚打开应用就被自动退出。同理，账号接口只要有一次成功回包就把计数清零，避免旧账和新的一次凑成「确认失效」。

之所以最终要自动退而不是长期留着：咪咕没有 refresh token，那张登录票据在第一次换票时就被消耗掉了，它换不来第二个会话——没有任何本机自愈手段，留着死凭据只会让界面长期卡在「登录可能已失效」，而唯一的出路本来就是重新登录。**单次信号绝不足以定罪**——删本机凭据不可逆，而服务端轮换、单接口抽风、风控抖动都会回同样的东西。**HTTP 403 不参与失效判定**（`classifySessionProbe()` 只把 401 算 revoked）：那大概率只是这首歌没有权益，`markRejected()` 依旧只把状态标成「可能失效」并保留凭据，绝不动登录。歌词、封面、CDN 时效地址、公开搜索这些不要求登录的接口回 401，也只留证据、不计数。**换票失败同样分级**（今天只有调试入口会发起它）：只有咪咕明确回 HTTP 401 才算「票据被拒」，才允许进入作废判定；网络中断、2xx 却没有下发新 `pacmtoken`、403/429/5xx，以及 `199999 系统繁忙` / `850002 内部错误` 这类服务端抖动，都只调 `markRejected()` 降级状态，凭据与票据原样保留，否则弱网或服务端抽风就会替用户把账记满。

### 登录探测诊断（调试版）

`checkPacMtoken` 成功路径上的轮换**是否真正延长服务端会话，目前仍是推断，不能当作已验证**（会话本身有多长，见下文「两小时这条时钟」一节）。2026-10-26 有了第一条真机记录：23:38 启动探测回 `000000`、响应带轮换头且本机确实写回了新值，次日 07:52 同一份凭据回 `850005 登录超时`。它证明轮换确实会发生并被本机采用，但也证明闲置过夜（这期间应用不在前台，保活没跑）之后官方仍然让会话超时；**它既不能说明轮换延长了会话，也不能说明是轮换把好 token 换坏的**，两种解释都还要继续取证。同日又有第二条：08:13、08:32、08:42 三次启动探测都回 `000000` 且每次都完成轮换，12:12 同一份凭据就改口 `850005`——间隔只有 3 小时 29 分，而那次自动续期也没换回新会话（`renewal → unknown`）。这条更倾向于「轮换不延长会话」，但仍然定不了论：这四次启动之间应用全在后台，整份记录里没有一条 `keep-alive`，服务端看到的也许就是一份从没被前台保活碰过的凭据。调试版在「设置 → 账户 → 登录探测记录（调试）」提供取证出口：启动探测（`trigger=startup`）、前台保活（`trigger=keep-alive`）每次记一条；`trigger=renewal` 现在只由「试一次续期」那个调试按钮写下，自动线路上的续期已经摘掉。保留最近 300 次，「复制记录」导出纯文本。

每条只包含时间、触发点、官方校验的 HTTP 状态/业务码/过滤后的文案、响应是否带 `pacmtoken`、本地是否真的换了值、是否复用了一次在飞探测、探测前/响应中/写回后的 Cookie 过期时间、探测前与写回后的凭据指纹及其来源，以及资料兜底的状态码和备注；**不含 `pacmtoken` 值、Cookie 值、手机号或票据**。正式版（`kDebugMode` 为假）不记录，也不显示入口。

凭据指纹（脱敏哈希 + 长度，不是可逆变换）回答的是「这一行到底是拿哪一份凭据去问的」：同一份凭据反复 `000000`、隔几小时突然 `850005`，两行的指纹能直接对上，不必再猜中间是不是换过值。它只是对号入座的记号，**不是服务端给的凭证版本**——咪咕不提供凭证新旧信息，本机一律不按到达顺序或本地写入时间判新旧，`来源`（导入 / 轮换 / Set-Cookie / 恢复 / 迁移）说的也只是这份值从哪条通道进来的。

同一节里几条与凭据状态有关的规则：认证凭证在本机只有一个落点（登录快照，网页别名 `mg_auth_pacmtoken` 与主名成对更新），不再存进 Cookie 罐，所以罐子按 `Expires` / `Max-Age` 的清理不会再把凭据悄悄换回原始导入值；服务端用 `Set-Cookie` 下发同名凭证时按凭证处理，但删除语义对认证凭证刻意不生效——到期说的是这条 Cookie 在本机该存多久，不等于服务端撤销了这份凭据，真撤销只有 `checkPacMtoken` 的回包说得准。并发防护方面，同一次登录会话里撞上的多次探测（启动预热与前台保活）共用一次 `checkPacMtoken` 请求，写回幂等，一份轮换最多落地一次；写回还认发起时的登录代际，期间退出或换号，回来的那张票一律被拒并计数，旧会话的结果盖不到新账号上。网页 profile 回收那条通道也不再改写认证凭证。

续期事件（`trigger=renewal`）也写进同一份记录，因为「这张票到底还换不换得动」是探测那条读不出来的：探测只说这次会话还认不认，说不出票据的本事。续期行不套官方/轮换/过期那三行，只写「本机已换新凭据=是/否」，能拿到时再跟上换票请求的 HTTP 状态与咪咕业务码（`票据码`，实测用过的票据是 `HTTP 200, 票据码 199999`；只存码，换票接口的服务端文案可能夹带请求内容，一律不存），最后一句结果——换到新凭据并写回、咪咕回包但没下发新的 `pacmtoken`、请求没到达咪咕、分不清票据问题还是服务抖动、明确回绝这张票据、本机没有留存票据（网页导入的会话没有票据）、已有一次续期在飞这次不叠加。有了这两个数，「200 但票据已经换不动」和「403 被风控挡在门外」才分得开；只有句子时两种情况长得一模一样。

码的读法后来补过两次，都是被真机数据逼出来的：业务码字段名 `status` 与 `code` 都可能出现，只认一个会把码读成空；正文偶尔不是 JSON（风控页、纯文本），这时 `票据码` 那格改写成 `回包 <形态>`（`非 JSON` / `空回包` / `JSON 里没有码` / `没有回包体`），否则这一行只剩一个 `HTTP 200`，分不清是咪咕认不下这张票据，还是本机根本没读懂它的回答。形态只描述形状，正文一个字节都不落。2026-10-26 的三次自动续期（12:12、12:55、15:24）全是 `HTTP 200` 且没有可用的 `pacmtoken`，那两格码当时读成空的，事后查明是本机只认 `status` 这个键名（见本节末），不是接口没给——`回包 <形态>` 那一格反倒一直没被真机用上。

同一个卡片里留着「试一次续期」按钮（仅调试版）：它当场用留存票据再换一次，结果写进同一份记录，一次落两行（发起标记与结果），也不叠在已经起飞的那次上。这个按钮就是为了证伪自动续期才加的：自动那条要等 `checkPacMtoken` 判失效才发起，那时票据多半早过了自己的期限，分不清「这张票换不动」和「这张票早就死了」；刚登录完几十秒按一次，票据 issuance 才几秒、同一份会话还回 `000000`，若这样都换不到新凭据，一次性就坐实了。2026-10-26 实测两次，全是 `HTTP 200, 票据码 199999`、不下发新 `pacmtoken`，结论就此定下，自动续期也从判定线路上摘掉。它现在是 `_renewSession()` 唯一的调用方，留着只为随时复测这条结论。

判定方法：连续观察数天，探测都成功且期间没有 401 / `290001` / `850005`，才能说轮换带来了滑动续期。这一条比原计划窄：原本还要求「响应中」的过期时间逐次后移，但 2026-10-26 的 13 条真机记录里三格过期时间**全是「无」**——`checkPacMtoken` 轮换回来的 `pacmtoken` 是不带 `Expires` / `Max-Age` 的会话 Cookie，本机根本读不到服务端期限。所以过期属性只能读成「没有证据」，不能读成「期限没变」，延长与否只剩下「长时间前台不掉线」这一条间接证据。续期那半边不必再取证了：`renewal → alive` 一次都没出现，登录后几十秒内按的两下都回 `HTTP 200, 票据码 199999` 且不下发新凭据——同一份会话此时还回 `000000`，却已经换不出第二份，票据一次性就此证完，本机不再指望它自愈。剩下唯一还要取的证是轮换延不延长会话，而能读它的只有 `keep-alive` 那几行；截至 15:55 的 18 条记录里，`keep-alive` 仍然是零条。

同一份记录里 12:55、15:24 两条续期只有 `HTTP 200` 没有码，15:46 之后同样一次请求却读出了 `199999`，读法修好之前那个「没有码」是本机只认 `status` 字段造成的，不是咪咕没给——同一个回包形状，只是键名换成了 `code`。另有一条现场读数的小坑：按「试一次续期」会落**两行**，前一行 `HTTP` 与票据码都为空、结果是「调试：主动发起一次续期」，那只是发起标记，真正的结论看紧接着的下一行。

### 两小时这条时钟

会话有多长这件事，2026-10-27 有了直接证据：网页登录那一次，咪咕在 `Set-Cookie` 里给 `.migu.cn` 的 `pacmtoken` 写了 `Max-Age=7200`——每份凭据从签发起只有两小时命，与用得多不多无关。`checkPacMtoken` 轮换走的是响应头里那份裸 `pacmtoken`，不带任何过期属性，本机读不到新期限，但它是一份刚签发的新凭据，时钟从头算起。这条把此前所有观察一次对齐：前台保活每 45–75 分钟问一次，六小时不掉线（每一问都落在两小时内）；关掉应用，隔 118 分钟回来仍是 `000000`，隔 120、149、210、494 分钟一律 `850005 登录超时`。「闲置就死」和「绝对过期」不是两种猜测，而是同一件事的两种说法。

还剩下的只有一个问题：轮换回来的那份新凭据，它的两小时是不是也从当下重新起算。轮换写回值被后续探测连续接受，说明咪咕认它；期限本身读不到，只能继续靠 `keep-alive` 那几行隔时间接验证。也正因为如此，**能不能在两小时内被问一次**成了本机唯一的实际杠杆——这就是 Windows 端「关闭主窗口后常驻托盘」这一项存在的原因。

### 关闭主窗口后常驻托盘（Windows）

实现放在 `lib/services/platform/desktop_tray.dart`，开关在「设置 → 账户 → 后台保持登录」，默认关闭，且只在 Windows 出现：Android 没有托盘，后台进程随时被系统回收，等价能力要另做前台服务，不能靠这个开关顺手承诺。

开启时依次做三件事：把 `SessionKeepAlive.allowsBackground` 置真、`windowManager.setPreventClose(true)`、用 `tray_manager` 挂一枚托盘图标并配上右键菜单（显示主界面 / 退出）。顺序有讲究——`setPreventClose` 必须先立起来，否则同一次点关闭会在监听器收到 `onWindowClose` 之前就把进程带走。此后点窗口上的关闭只是 `hide()`，进程留着，`_sync()` 因为允许后台而照常排下一次探测：用的还是同一件 `checkPacMtoken`，不多带内容、不去新的域名。收起窗口时顺手 `PlayerProvider.pause()`——用户点的是「关闭」，让曲子从已经看不见的窗口里继续响会让人以为程序没退出。双击托盘图标 `show()` + `focus()` 回到主界面；菜单里的「退出」先把 `allowsBackground` 落回假、拆掉托盘，再 `windowManager.destroy()`，最后 `exit(0)`：播放与全局热键插件都留有原生线程，只销毁窗口不足以让进程收干净。

关掉开关即完全恢复原样：`setPreventClose(false)`、`trayManager.destroy()`，保活重新只跟着前后台走。失效判定那条不受影响——`SessionKeepAlive.stop()` 之后 `allowsBackground` 也唤不醒它，`test/session_keep_alive_test.dart` 单独钉住这一条。配套的对外说明：隐私政策新增「关闭主窗口后常驻托盘（Windows 可选）」一条，「日志与第三方组件」「系统权限」两条也写上了窗口与托盘组件；`test/compliance_text_test.dart` 断言政策条数、界面文案与代码三处一致。

### 原生登录（短信验证码 / 账号密码）

1. 弹窗上半部分是当前登录状态（未登录 / 登录已失效，已自动退出 / 已保存登录凭据 / 登录凭据已验证 / 登录可能已失效 / 已登录，缺少音乐登录会话），下半部分是两个胶囊式页签切换的登录方式（`_ModeTabs`），整屏不出现网页。表单按紧凑样式排布：输入框不再另起字段标题，提示词即字段名，提交按钮是整宽描边的「登录」。
2. 短信方式填手机号后点「发送验证码」，按钮进入 60 秒倒计时（显示「30s 后重发」）；把收到的验证码填进来点「登录」。密码方式填账号与密码，密码框默认遮蔽、可点眼睛图标临时显示。手机号、验证码与密码没填齐时提交按钮保持禁用。
3. 咪咕若要求图形验证码，表单里会多出「图形验证码」一行：左边是输入框，右边是咪咕下发的那张图片，点图片就是官方的「换一张」。这一行出现后，不填字符提交按钮一直禁用；点提交时应用先让官方认一次你输入的字符，认过了才带着它重新提交登录，认不过就提示换一张重填。图片由你本人识别，应用不代答、也不引入任何识别能力。咪咕改要滑块这类本表单无法呈现的形式时，只在「需要官方页面协助」里说明并给出「打开咪咕官方登录页」入口。
4. 手机号、验证码与密码只在输入框内存里存在；提交成功后立刻清空验证码、密码与图形验证码输入框并关闭弹窗，再提示「登录成功：138\*\*\*\*0000」。表单下方常驻一个「改用咪咕官方页面登录」的小按钮，任何时候可以直接走官方页面。
5. 登录成功后写入安全存储的是 `token-validate` 下发的 `pacmtoken` 和本次登录票据。界面状态直接标记为「登录凭据已验证」（咪咕服务端刚刚发放了会话），并重启前台保活、拉一次账号资料。

原生登录走的是咪咕网页端自用协议，官方随时可能调整参数或加风控。图形验证码已经做成表单里的一行，由你自己看、自己输；除此之外一旦被拒，只剩官方页面登录这一条兜底路径，应用不会自动重试或后台重登（咪咕没有 refresh token，那张登录票据又已经在登录时用掉，本机没有任何自愈手段——掉线只能重新登录一次）。

写入本机的登录凭据只有 `pacmtoken` 与那张登录票据——`uid` / `msisdn` 由官方签名上下文推导，登录响应里没有可靠对应值，猜错反而会让取链请求整体被拒。前台保活探测的门槛也只看 `pacmtoken`：原生登录拿到这一份凭据也会每 45–75 分钟校验一次，先调官方 `checkPacMtoken`（只带 `pacmtoken`，成功时把响应头里轮换的新值写回本机并清零旧证据），它说不清时再用账号资料确认。账号资料接口对缺 `uid` 的请求同样回 `290001 请先登录`（见上一节），所以本机没有 `uid` 时这条兜底只归为 unknown，既不报失效也不计证据；此时能不能读出头像是由那份 `pacmtoken` 之外的东西决定的，界面读得到头像昵称说明凭据完整，读不到也只说明这个接口要的参数本机没有。真正判凭据的还是 `checkPacMtoken`。

### 咪咕官方页面登录（风控兜底，按需打开官方登录窗口）

1. 在账号弹窗里点「改用咪咕官方页面登录」（或风控提示下的「打开咪咕官方登录页」），此时才打开 `lib/pages/official_login_page.dart` 这个只承载官方通行证页面的登录窗口，在其中完成咪咕通行证登录。登录方式以官方页面为准；当前官方页面提供短信、密码或本机号码登录。
2. 登录地址由 `lib/services/auth/migu_passport_url.dart` 按官方页面的全页登录格式构造，除 `sourceid` 等官方参数外还带上 `relayState`（回跳地址为 `https://music.migu.cn/v5/`）；缺少它时通行证登录后不会回跳，页面会一直停在加载态。
3. 回跳后应用会短暂读取该窗口的 Cookie（约 16 秒，每 0.9 秒一次），只有出现对 `music.migu.cn` 生效的登录凭据（`pacmtoken`、`mg_auth_sid` 或 `migu-utoken-sessionid`）才算登录完成并导入。匿名访问咪咕网页本来就会写入的统计与设备 Cookie（`cookieId`、`mg_uem_user_id_*`、`migu-device-uuid`、`task-session-id`）一律不作为登录依据，只对通行证域生效的 Cookie 也不会触发导入、不清空网页会话。
4. 实测结论（真实账号，2026-10-20）：整页 WebView 里官方页面确实显示已登录（头像与会员标识都在），可读到的 13 项 Cookie 主要是 `LtToken`、`USessionID`、`mgnd_session_*` 等通行证级会话，其中包含 `pacmtoken`，但没有 `mg_auth_sid`。这不是读取能力的限制——`mg_auth_sid` 由页面脚本（js-cookie）写入，脚本写不出 HttpOnly，而 Windows 端读取走 CDP `Network.getCookies`，HttpOnly 也会返回。2026-10-21 定位到：音乐页自己的「登录」按钮并不整页跳转，而是在 `music.migu.cn` 页面内嵌一个 `passport.migu.cn/login?…&callbackURL=PostToken` 的 iframe，由父页面收下回票后用脚本写入 `mg_auth_sid`；把通行证页当整页顶层文档打开时缺少这个父页面，那一步换票回调不执行。不过 `pacmtoken` 仍会出现，原生 VIP 取链只需要它，因此登录窗口现在会以它为完成信号自动导入；等待窗口仍只有 16 秒。
5. 登录窗口顶部的地址栏显示当前真实域名与检测状态，用于区分“还停在通行证页”和“已回到音乐页但凭据未写入”。若未自动返回，可点击「我已登录，读取凭证」手动触发：读到音乐域登录凭据时按正常流程导入并清空网页会话；只读到官方 `mg_auth_*`（如 `mg_auth_pid`，说明换票尚未完成）时也导入，但保留网页会话并在提示中列出已看到的官方 Cookie 名称；只有统计类 Cookie 时只提示、不导入。提示中只出现 Cookie 名称，不显示任何 Cookie 值。
6. 读取成功后该窗口立即清理 Cookie 并关闭，应用自动回到首页，账号弹窗也一并关闭；其余界面上没有任何网页元素。

WebView 只出现在两个地方：按需打开的官方登录窗口临时加载通行证页面，播放页为 VIP 曲目内嵌咪咕官方网页播放器；账号弹窗、原生登录面板与其余界面都不加载任何网页。官方登录窗口通过系统 WebView 的 CookieManager 读取 Cookie（包含 HttpOnly 与会话 Cookie）；个别时机 CookieManager 读不到页面刚写入的条目，还会直接读页面自己的 `document.cookie` 作为兜底（只取名称与值）。读到的登录会话交给同一套安全存储与请求逻辑。内嵌播放器面板完全不接触 CookieManager。Windows 上两者使用相互隔离的用户数据目录；Android 共用系统 WebView 的 Cookie 库，退出登录页时只按咪咕站点逐条删除登录 Cookie。

Cookie 保存在系统安全存储中（Windows 是由 DPAPI 按当前账户加密的密文文件，落在应用数据目录；Android 使用 Keystore 派生密钥加密，且已关闭系统备份），仅发送给咪咕域名。旧版 SharedPreferences 中的明文数据会在首次启动时迁移，迁移并回读成功后才删除旧数据；迁移失败会保留旧数据并在界面提示，不会静默写回明文。

登录状态分为“已保存登录凭据”“登录凭据已验证”“登录可能已失效”，另有“已登录，缺少音乐登录会话”。带 `pacmtoken` 的 VIP 取链请求成功、原生登录刚换到音乐站会话、或调试入口真的换回新凭据时标记为已验证，并把「账号接口被拒」的计数清零；只有要求登录的账号接口在本机确实带过 `pacmtoken` 时回 HTTP 401 或业务码 `290001 请先登录`，才算一次失效证据，单次证据只把状态标成「可能失效」并**保留凭据**，隔过 30 分钟后再次被拒才按上文「登录失效时自动退出」当场清掉本机凭据；403 只说明当前账号大概率没有这首曲目的权益，公开接口（歌词、封面、搜索）的 401 也只说那条资源拿不到，两者都不参与失效判定，不翻转也不清除登录。取链接口在业务层返回“没有可用地址”（如 `440022`）时只展示服务端文案，不改变登录状态；`listenSong.do` 的 `200002` 属于接口层拒绝，同样不改变状态。重启后不会直接沿用上次的“已验证”状态。原生登录只由用户当场发起，应用绝不自动重登，也不在接口回绝时用留存票据换一次会话（那张票已经用过，换不来新会话）；官方网页本身会续签会话，Windows 上内嵌播放器打开时由 `WebSessionSync` 把续签结果读回本机快照（Android 不读回，网页会话只留在系统 WebView 里）；其余情况只能被动保留服务端新的 Set-Cookie。

官方窗口导入提示的项数是写入时的数量；服务端随后用 `Max-Age=0` 删除的 Cookie 不会由本地快照复活，因此账号卡片上显示的项数可能更少（例如导入 8 项后剩 5 项）。每次重新登录都会清空旧快照与旧的服务端会话，避免不同账号混用。

若本机凭据里没有 `pacmtoken`、`mg_auth_sid` 或 `migu-utoken-sessionid` 这类登录凭据，界面会显示“已登录，缺少音乐登录会话”，VIP 播放会直接说明缺少 `pacmtoken`，而不是笼统地提示“登录可能已失效”，并且不会把状态标记为“已失效”。

VIP 曲目能否播放完全取决于咪咕是否按当前账号权益发放地址：应用只把本机凭据随请求发送，不做本地提权，也不下载或解密音频；被咪咕拒绝时，播放页的「官方播放器」面板仍可作为兜底——那是咪咕自己的页面，登录、鉴权、取链都在它那边完成。界面文案与错误提示按这一分工措辞，不承诺“登录后即可播放任意 VIP 曲目”。

## 版本检查

关于页的「立即检查」在应用内完成，不再直接跳浏览器：`lib/services/app_update_service.dart` 匿名 GET `https://api.github.com/repos/ChenL-eon/MiguGo/releases/latest`，从返回的 `tag_name` 里取版本号与 `AppConstants.appVersion` 逐段比大小，结论（已是最新 / 有新版本 / 这次没查到）显示在卡片上，只有查到新版本时才多出一个「打开发布页」的入口由用户点。请求不带 Cookie、不带 Authorization、不带设备标识，仓库是 public，匿名可读；下载与安装都不在这个流程里发生。

`lib/providers/update_provider.dart` 把结论落在本机偏好（`migu_update_check_result_v1`，只存状态、版本号与检查时间），重启后仍能看到上次查到了什么；失败不覆盖上一次的好结果。启动时的自动检查（`main.dart` 在 `runApp` 之后 `unawaited(updates.checkOnStartup())`，不挡首帧）受「启动时自动检查」开关控制，并且 12 小时内不重复请求，避免反复开关应用去撞 GitHub 的匿名限流。

## 合规实现约定

项目在实现上固定遵循以下约定：

- 播放音质只使用咪咕官方的四档标识：`PQ`（标准音质）、`HQ`（高品质）、`SQ`（无损音质）、`ZQ24`（至臻 24bit）。应用按所选档位请求，账号没有对应权益或曲目没有 24bit 时逐级回退；免费曲目最终仍可回退到 `listenSong.do` 的标准音质。不实现音频下载、音频文件解密或本地音频持久化，也不通过改写 CDN 目录等方式绕过服务端权益判定。
- 免费曲目的地址由 `listenSong.do` 以 302 临时重定向下发；VIP 曲目的地址由 `strategy/pc/listen/v2.0` 按账号权益下发。两种地址都直接交给 `just_audio` 在线流式播放；因链接过期导致加载失败时，同一首歌会自动重取一次，仍失败就提示重试。
- VIP 曲目只有在**本机存在 `pacmtoken` 凭据**时才发起取链请求；接口没给地址时，提示里转述咪咕返回的 `dialogInfo` 文案（如“会员专属音质”），不做任何本地提权，同时保留「官方页面播放」入口作为兜底。
- 所有请求自动携带 `Referer: https://music.migu.cn`、本机 `deviceId` 以及已有的 `uid` / `pacmtoken` / `msisdn` 请求头；Cookie 只附加到 `migu.cn` 及其子域，不写入日志、不在界面显示具体值。
- `deviceId` 由 `lib/core/utils/device_identity.dart` 提供：Android 通过 `MainActivity` 的 `migu_lele/device` 通道读取 `Settings.Secure.ANDROID_ID`，Windows 等其他平台首次启动生成随机 UUID 并存在本机偏好里。它只是一个稳定的设备侧标识，用来把同一账号的多端会话区分开，不参与任何登录签名，也不读取 IMEI、序列号等敏感信息。
- 服务端通过 `Set-Cookie` 下发的 Cookie 优先于手动快照；应用按 `Domain`、`Path`、`Secure`、`Max-Age`、`Expires` 更新、替换或删除。只有 Cookie 罐里确实还有可用的同名值时才压住手动快照，因此服务端轮换会覆盖旧值，而一次 `Max-Age=0` 删除不会让登录凭据从此不再发送。`pacmtoken` 与网页快照里的别名 `mg_auth_pacmtoken` 指向同一份会话：取凭据时优先 Cookie 罐里的 `pacmtoken`，其次是快照里的别名；调试入口换到的新值与 `Set-Cookie` 轮换都会同步别名，避免旧别名压住刚换到的新值。登录快照（`mg_auth_pacmtoken`、`mg_auth_uid`、`mg_auth_msisdn` 等）本身不带过期时间，整个 Cookie 罐也会全量备份进系统安全存储并在启动时重建，所以重启动不会丢登录态。
- 咪咕没有 refresh token，失效只能由用户重新登录。原生登录时通行证签发的登录票据也会留在本机（`PassportTicketStore`，与 Cookie 分开存放），但它不再参与失效判定：这张票在登录那一次 `token-validate/v3.0` 里就被咪咕消耗掉了，再拿它换一次只回 `HTTP 200, 票据码 199999`，2026-10-26 用刚签发几十秒的票实测确认，本机因此没有自动换票这一步，票据只留给调试版复测。应用因此另有**前台保活**（`lib/services/auth/session_keep_alive.dart`，只在应用可见时每 45–75 分钟校验一次：先调官方 `checkPacMtoken`，成功时顺带写回响应头里轮换的 `pacmtoken`；它说不清时再用账号资料确认。退到后台立即取消定时器——Windows 上开了「关闭主窗口后常驻托盘」这一项时前后台一律继续排期（`allowsBackground`，见上文同名小节），启动时由 `main.dart` 的 `_warmUpSession()` 先做一次同样的探测，再拉资料与歌单，避免旧的被拒证据先被新一轮请求凑数）与**鉴权失败取证**（判定放在拦截器里，因为只有那里拿得到真实请求地址——业务码 `290001 请先登录` 是随 HTTP 200 回来的。只有本身就要求登录的账号接口，即 `isLoginScopedEndpoint()` 认下的用户资料与账号歌单那几个路径，在本地确实带过 `pacmtoken` 时回绝，才算一次失效证据；账号歌单与 `queryUserInfo` 还要本机有 `uid`，否则「缺 uid」回出来的 `290001` 会冒充失效。歌词、封面、公开搜索的 401 与 HTTP 403 只留记录、不参与判定，未登录的公开请求更不会骚扰用户）两套机制。证据由 `SessionRejectLedger`（`lib/services/auth/session_reject_ledger.dart`）记下最近一条：接口地址、HTTP 状态码、业务编码与那句服务端文案，服务端文案先经 `sanitizeInfo()` 过滤，不含任何凭据内容。第一次回绝只把状态降级为「登录可能已失效」并**保留凭据**；隔过 30 分钟（`confirmGap`）且仍在 24 小时（`strikeWindow`）内，账号接口再次回绝，才认定这份凭据确实作废，于是保活永久停摆并自动走一遍退出登录（清凭据、清账号快照、停止播放并清空队列），登录面板顶部直接引用那条证据，说明是咪咕拒绝而不是用户自己退的。期间账号接口只要有一次成功回包就把计数清零，重新登录与手动退出则连证据一起清掉。失效判定不夹任何换票动作，两次取证之间也没有冷却：一次在飞的调试换票不叠第二次裁决，等它自己收尾。应用不会自动重登，官方页面登录根本没有登录票据。
- 不生成官方登录签名、不做音频解密、不批量抓取；官方登录窗口读到凭证后立即清理其 WebView 会话并关闭。Windows 上内嵌播放器与登录窗口使用相互隔离的浏览器目录，清理时只清登录目录，不会抹掉播放器 profile 里咪咕写入的会话；Android 两处 WebView 共用系统 WebView 的 Cookie 库，登录页退出时按咪咕站点逐条删除 Cookie，不整份清空。Windows 的播放页还会同步本机账号的登录会话 Cookie；页面本身只允许停留在 `https://*.migu.cn`。
- 首页推送直接使用咪咕网页的推荐模板数据，应用只补一个本机生成的 `imei` 设备号，不伪造账号身份，也不缓存推荐结果到磁盘。
- 外部歌单导入使用独立的网络客户端：不带咪咕 Cookie、不带第三方 Cookie、不读取浏览器数据，只对用户主动粘贴的链接发起公开 GET 请求；不登录第三方平台，也不把外部歌单的音频地址带进应用。
